# GAPS v2 — where the thesis itself leaks (2026-06-28)

Status: provocations · Owner: ROLE_ARCHITECT

GAPS.md (and the A0xx TSPECs) are the *implementation* backlog — constraint extraction, route
detection, CLI verbs. This file is different: these challenge the **claim**, not the code. RIR
promises a capability is "completely implemented, correctly connected, documented, and **verifiably
executable end to end**." Each gap below is a way that sentence is currently false even when every
test is green and every capability reads `CLOSED`.

---

## Theme A — Topology is not truth

**V1. CLOSED proves the wires are connected, not that current flows.**
Closure checks that a route→controller→service→repository→db→response *path of nodes exists and is
linked*. It says nothing about behavior: the service can call the repo and ignore the result; the
auth guard can be present and always return `true`; the query can hit the wrong table. A backdoored
`login()` that returns a token for any password is **CLOSED**. We prove plumbing, not semantics. →
Closure needs a behavioral tier: link a capability to the test(s)/dataflow that actually exercise
*that* path, not just the existence of nodes.

**V2. "Verifiable executable" with nothing ever executed.**
"Verifiable" today means "the static graph says it could run." Nothing runs. The out-of-the-box
move: RIR already knows the route, the input shape (from constraints), and the expected output
(`JWT`) — so it can **synthesize a probe** (hit the route, assert 200 + JWT shape) and only then
promote a capability from `CLOSED` (statically connected) to `EXECUTABLE` (observed). Until that
exists, the headline verb is unproven.

**V3. Closure is binary; evidence is graded — and the two never meet.**
`EvidenceIR.confidence` exists (1.0 for AST, lower for inference) but closure collapses to
CLOSED/BROKEN. A capability `CLOSED` via a fuzzy controller-name guess is indistinguishable from one
proven by an explicit typed call. There is no **weakest-link confidence** propagated to the
capability, so "CLOSED" hides how much you should trust it. → graded closure that surfaces its least
certain edge.

**V4. The static compiler is blind to the runtime graph.**
DI containers, decorator wiring resolved at boot, event buses connected by a string topic,
middleware chains, feature flags, ORM lazy relations, plugin registries — these edges exist only at
runtime. A capability wired through a message queue is `BROKEN` in the static view; one wired through
a flag that's off is `CLOSED` but dead. `EvidenceSource.RUNTIME` is in the IR and **nothing produces
it**. Determinism is the project's virtue and its ceiling: we see the *declared* graph, not the
*executed* one. → fuse a trace/boot-time evidence source; reconcile static vs runtime edges.

## Theme B — The model is too thin for real capabilities

**V5. No negative space — RIR can only assert presence, never required-absence.**
Correctness and security are mostly about what must NOT be there: this route MUST require auth; PII
MUST NOT flow to logs; an admin action MUST pass an authz node. Execution closure models positive
connectivity. There is no **guard/policy closure** — "every BACKEND_ROUTE for a non-public
capability traverses an AUTHZ node before the REPOSITORY." That's an entire second closure type, and
it's the one security actually cares about.

**V6. The capability is a single happy path, but real capabilities are state machines.**
`expectedChain` is one linear pipeline. LOGIN really has success / MFA-required / locked-out /
rate-limited / password-expired branches; CHECKOUT has payment-failed / out-of-stock / partial. A
capability missing all its error/alternate paths looks **identical** to a complete one. We check that
*a* path closes, never that the capability's required *state space* is covered. → model alternate &
exception paths as part of the expected shape.

**V7. Docs are trusted as ground truth.**
Requirement IR treats a markdown "MUST" as fact. Docs lie, go stale, and are aspirational. A
`DOC_UNMAPPED`/`UNIMPLEMENTED` derived from a 2-year-old design note carries the same weight as one
from the signed-off spec. There is no **requirement authority/freshness** (PRD vs README TODO vs
autogenerated API doc; last-touched vs code). Severity should bend to *which* document said it.

**V8. No criticality — every capability weighs the same.**
`PAYMENT.REFUND` BROKEN and `PROFILE.UPDATE` BROKEN are reported identically. Without a risk/
criticality weight, the report can't answer the only question that matters operationally: "is any
*critical* capability not *securely* closed?" Criticality × guard-closure (V5) × confidence (V3) is
the actual signal.

## Theme C — The boundaries are drawn in the wrong place

**V9. The repo boundary is not the system boundary.**
A capability whose UI is in repo A, API in repo B, auth service in repo C (linked by HTTP/gRPC/
queue) is `BROKEN` in *every* repo, because the edge leaves the repo. `rir compile <dir>` can never
see a distributed capability close. → multi-repo IR linking: stitch capabilities across repos by
their API/contract schema (the response of B's route == the API_CALL of A).

**V10. There is no "what this product is supposed to be."**
Consistency findings are computed against the *global* 22-feature ontology, so any real repo reports
a flood of `UNIMPLEMENTED`/`UNDOCUMENTED` for features it was never meant to have. Without a
per-repo **scope manifest** ("this product claims AUTH + TEAM + SCHEDULE"), `UNDOCUMENTED` and
`UNIMPLEMENTED` are noise. Scope is what turns the cross-engine from a curiosity into a gate.

**V11. The IR is a snapshot; drift is a time-series.**
"Documented vs implemented vs consistent" is judged at one commit. The valuable question is
directional: which capability regressed `CLOSED→BROKEN` this PR, which requirement has sat
`UNIMPLEMENTED` for N releases, which doc describes v1 while code is v2. Snapshot packages exist and
are unused. → closure-over-time + a CI gate that fails a PR moving any capability *away* from closed.

---

### If I had to pick three to change the product's truth-value
1. **V5 guard/negative-space closure** — unlocks security, the highest-value question RIR can't ask.
2. **V10 per-repo scope manifest** — without it the consistency report is unusable on real repos.
3. **V2 executable probe** — turns "verifiable" from a claim into an observation; also subsumes V1.
